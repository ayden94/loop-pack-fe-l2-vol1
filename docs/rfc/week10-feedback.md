# 9주차 피드백 대응 — volume-10

## 범위와 기준선

2026-09-08 종합 피드백을 `main`의 `72a49cd1` 기준으로 반영한다.
이 기준선은 `origin/volumn-9`를 병합한 코드다. 리뷰 대상 `volume-9`와 달리
401개 테스트이며, 해당 브랜치의 추가 fixture 구현을 임의로 가져오지 않는다.
proxy의 쿠키 존재 확인과 서버·API의 서명·만료 검증 경계는 유지한다.

장바구니 정책은 사용자 제안 중 **로그아웃 시 비우기**를 선택한다. 계정별 장바구니
보관함을 새로 만들지 않으며, 익명 사용자가 담은 상품의 로그인 복원은 유지한다.
위시리스트는 주문 입력이 아니므로 기존 기기 소유 정책을 유지한다.

## 회귀 검증의 계약

- `AuthProvider.dom.test.tsx`: 초기 로그인 snapshot 뒤 `/me` 401, 새 서버 snapshot,
  로그아웃과 진행 중 조회의 경합을 보호한다. Query 알림과 요청 abort에 직접 구독한다.
- `OrderSession.dom.test.tsx`: 조회·주문 생성 모두 실제 Service 설정을 사용한다.
  `/me`는 유효한 사용자를 반환하게 해 주문 연결 결함을 가리지 않는다.
- `LogoutButton.dom.test.tsx`: 성공 시 persist 재수화까지 빈 cart, 실패 시 인증·cart 유지.
- `ToggleWishlistButton.dom.test.tsx`: 실제 두 번의 클릭에 추가·해제 결과가 각각 계측됨.
- `ExpiredSessionCookie.test.ts`: baseURL에서 쿠키 scope를 파생.
- `auth-lifecycle.spec.ts`: 전체 새로고침 없는 만료 이동에서 본문과 헤더 일치,
  계정 교차 후 이전 상품으로 주문할 수 없음.

이번 피드백으로 추가하는 브라우저 회귀는 위 두 결함에만 한정한다.
목록 탐색·위시리스트를 별도의 장시간 E2E로 늘리지 않는다.
기존 익명·유효 인증·만료 진입 조건과 proxy matcher 테스트는 유지한다.

## 관측한 검증

- 위시리스트: 수정 전 이벤트 배열이 비어 실패 → 수정 후 통과.
- 쿠키: 수정 전 IP·도메인 두 경우 모두 `localhost`로 실패 → 수정 후 통과.
- 인증: 수정 전 401 뒤에도 `authenticated`여서 실패 → 수정 후 통과.
- 장바구니: 수정 전 로그아웃 뒤 `{ p1: true }`가 남아 실패 → 수정 후 통과.
- `OrderService` 두 `requiresAuth` 제거: 실제 조회·mutation 테스트 모두 실패.
- `AuthExpiryBridge` 렌더 제거: 같은 두 테스트 모두 실패.
- 두 변이를 복원한 뒤 통과. 임시 변이는 제품 코드에 남기지 않았다.
- production에서 새 만료·계정 교차 E2E 2개 통과.

## 앞으로의 변경 점검

1. 서버 상태는 캐시가 소유하고 SSR props는 seed인지 확인한다. 공유 layout의
   재마운트를 상태 갱신 계약으로 가정하지 않는다.
2. 인증 경계 테스트는 실제 Service 설정과 production Provider를 함께 통과한다.
   meta·bridge 제거 실험처럼 연결 한 곳이 빠졌을 때 실패하는지 확인한다.
3. persist 정책은 저장 매체가 아니라 **소유자와 종료 이벤트**를 기준으로 결정한다.
   로그인 성공뿐 아니라 로그아웃 실패·성공·다른 계정·새로고침을 확인한다.
4. 기능 제외를 쓰기 전 저장소에서 구현·호출자·대체 테스트를 검색하고 실제 경로를 남긴다.
5. 테스트의 host·계정·쿠키 scope는 실행 환경 한곳에서 파생한다.

AI가 코드·회귀 테스트·문서 초안을 작성했으며, 이 문서의 검증은 실행 결과만 기록한다.
